# Axoneme-CLI - V2 proposal

### 1. The Data Layer: SQLite as the Embedded Source of Truth

Currently, the system uses the file system as its primary database. To render the Kanban board, the Python engine physically opens every markdown file, parses the YAML frontmatter with regex, and sends it to the UI. This is incredibly expensive and fragile.

* **The Upgrade:** Introduce an embedded, zero-configuration database like **SQLite** or **DuckDB**.
* **Markdown as an Artifact, Not a Database:** The `.tracker` markdown files should be treated as Git-friendly *exports* or *artifacts*, not the live database. When the daemon boots, it indexes the `.tracker` files into SQLite. All UI queries, filtering, and sorting happen against the fast SQL layer.
* **CQRS (Command Query Responsibility Segregation):** When a ticket is moved, the backend writes the mutation to SQLite (fast) and dispatches a background task to update the physical markdown file (slow), keeping the UI incredibly snappy.

### 2. Frontend State: Unidirectional Data Flow

Right now, `app.js` is a massive monolith where state is inextricably bound to the DOM. The UI reads from the DOM to know what state it is in, which leads to ghost states and the need for a "Full Refresh" button.

* **The Upgrade:** Adopt a strict Unidirectional Data Flow (UDF) using a lightweight reactive framework (like Preact, Svelte, or even just a Vanilla JS state container like Zustand).
* **State Separation:** The UI should be a pure function of a centralized state object. When data arrives from the API, it updates the state store. The UI simply reacts to the store. No more querying `document.getElementById('modal-text').value` to figure out if a file is dirty.

### 3. File Orchestration: The Virtual File System (VFS)

The Yomama Sync Bridge currently operates by reading a file, manipulating it as a string in memory, and immediately overwriting the physical file.

* **The Upgrade:** Implement an in-memory Virtual File System (VFS) layer.
* **Atomic Commits:** When the LLM patches multiple files, the modifications occur in the VFS. The system can then run its AST syntax checks (Python/JS) against the VFS state. Only if the *entire* transaction passes does the VFS perform an atomic flush to the physical disk. If one file fails, the whole transaction rolls back, preventing half-patched codebases.

### 4. Background Processing: Event Loops & Task Queues

Context gathering and diff generation currently block the main Flask thread. If a workspace grows massive, compiling the context payloads will cause the UI to hang.

* **The Upgrade:** Offload I/O-heavy operations (context generation, Git diffing, file archiving) to an asynchronous worker queue.
* **WebSockets/SSE:** Instead of the UI polling or waiting for a massive HTTP response, the backend should communicate over Server-Sent Events (SSE) or WebSockets. The UI requests a context compile, the backend immediately returns a `202 Accepted`, and streams progress events ("Mapping API...", "Compressing UI...") until the job is done.

### 5. Infrastructure: Deterministic Process Management

The `axoneme-service.sh` script relies heavily on `tmux` to manage multiple running emulators and APIs. While visually cool, `tmux` is an interactive terminal multiplexer, not a deterministic process supervisor.

* **The Upgrade:** Migrate to a robust process manager like **Supervisord**, **PM2**, or a native Go-based runner (like `goreman`). These tools are specifically designed to monitor stdout/stderr, handle automatic restarts, manage environment variables deterministically, and provide structured logging without relying on virtual terminal sessions.


# comments on the existing ticket and Phase ordering


That existing ticket is actually the perfect catalyst for the entire refactor. If you try to implement reactive state management (Pillar 2) or stream data over WebSockets (Pillar 4) while `app.js` is still a 2,000-line monolith, the cognitive load and regression risk will be catastrophic.

Here is the deterministic order of operations to merge your existing ticket with the broader architectural blueprint, ensuring that each phase physically enables the next without breaking the application in the interim.

### Phase 1: Structural Splintering (Your Existing Ticket)

This is purely mechanical and carries zero backend risk. You isolate the frontend domains without changing how they communicate with the server.

* **Action:** Execute ticket `CLI-QUEUE-20260622_2241`.
* **Result:** `app.js` becomes an orchestration shell importing tightly scoped modules (`bridge.js`, `kanban.js`, `gather.js`). All global variables (`currentTasks`, `contextManifest`) are quarantined into a naive `store.js`.
* **Why here?:** You cannot build a clean Unidirectional Data Flow until the domain logic is physically decoupled.

### Phase 2: Frontend State Hardening (Pillar 2 - UDF)

Now that you have a `store.js` file, you upgrade it from a "dumb bucket of global variables" into a strict state machine.

* **Action:** Implement a reactive state manager (Vanilla JS PubSub, Zustand, or Alpine/Preact) inside `store.js`. Refactor the modules (`kanban.js`, `bridge.js`) so they no longer read from the DOM (e.g., `document.getElementById('modal-text').value`). Instead, they dispatch actions to the store, and the DOM subscribes to store updates.
* **Why here?:** Before we change the backend APIs or start streaming data, the frontend must be deterministic. If the UI only renders based on `store.js`, the backend can change how it delivers data without breaking the UI.

### Phase 3: The Data Layer Swap (Pillar 1 - SQLite)

With the frontend strictly listening to state payloads, we can gut the expensive, blocking backend logic.

* **Action:** Rip out the backend Python logic that opens hundreds of `.tracker` markdown files using Regex. Implement an embedded SQLite/DuckDB index.
* **Result:** The API endpoints (`/api/tracker/files`) stop reading the disk and start querying the database. The frontend doesn't notice the difference, but response times drop from seconds to milliseconds.

### Phase 4: Asynchronous I/O & Streaming (Pillar 4 - Event Loops)

Now that the database is fast, we need to fix the heavy context/compiler engines that block the web server.

* **Action:** Move `engine_gather.py` and `compiler.py` into background task queues. Add a WebSocket or Server-Sent Events (SSE) layer to `app.py`.
* **Result:** When you click "Full Refresh" in the UI, the frontend doesn't hang waiting for an HTTP response. The backend accepts the job instantly and streams progress events (`"Compressing JS..."`, `"Mapping Contexts..."`) to the frontend's reactive `store.js`.
### Phase 5: The Virtual File System & Semantic Strategy Pattern (Pillar 3 - VFS)

This is the most complex surgical operation on the core chassis.

* **Action (The VFS):** Rewrite the Sync Bridge (`engine_bridge.py`). Instead of applying patches string-by-string and immediately writing to disk, it routes the patches into an in-memory VFS. It verifies the syntax of the entire VFS matrix, and only commits to physical disk if the transaction is mathematically perfect.
* **Action (Semantic Strategy Pattern):** Evolve the bridge from a generic text replacer into a file-type-aware routing engine:
    * **Strict Engine (Python/YAML):** Absolute whitespace tracking, statistical step math, and strict line-by-line matching.
    * **Structural Engine (JS/TS/Rust):** Whitespace agnostic. Flattens strings for matching, injects, and pipes the output through native AST formatters (e.g., Prettier) before committing.
    * **Object Engine (JSON):** Bypasses text diffs entirely. Parses `SEARCH`/`REPLACE` blocks as actual dictionaries and recursively applies JSON tree patches.
    * **Fuzzy Engine (Markdown/Text):** Flattens arrays and uses Levenshtein distance to survive LLM line-wrapping token-limit hallucinations.
* **Why here?:** Doing this *after* the UI, DB, and async queues are stabilized means you have a rock-solid observability platform to debug the VFS if things go wrong.
### Phase 6: Infrastructure Polish (Pillar 5 - Process Management)

The final seal.

* **Action:** Eradicate the `axoneme-service.sh` tmux spaghetti. Write a clean `supervisord.conf` or `pm2` ecosystem file that manages the Tailscale routes, the FastAPI backend, and the background workers deterministically.

## 🛠️ Unified inSetu Frontend Stack Standards (Ratified 2026-06-25)

To maintain a zero-bundler, high-performance, and deeply portable ecosystem, the following four-way unified stack is locked down as the architectural standard:

### 1. View & Presentation: LitElement (Lightweight Custom Elements)
* **Paradigm:** Native browser Web Components. Bypasses the virtual DOM completely.
* **Styling Rules:** Strict **Scoped CSS** encapsulated natively inside the dynamic components. Global namespaces collapse into structural CSS variables (`--bg`, `--pane-bg`, `--text`), keeping element template markup entirely clean of class pollution and compiler overhead.

### 2. State & Core Machine: Zustand (Vanilla Integration)
* **Paradigm:** Centralized, fine-grained Publish/Subscribe state container.
* **Execution:** Components explicitly bind to the store via standard lifecycles (`connectedCallback` / `disconnectedCallback`). State changes update granular nodes directly without executing expensive parent layout re-render loops.

### 3. Layout Infrastructure: Classless Grid Framework (Optional Baseline Tokens)
* **Paradigm:** Semantic layout markers target standard structural tags natively.
* **Execution:** Eradicates visual script string clutter, allowing component templates to prioritize pristine markdown rendering and clear textual lines.

### 4. Data Layer Architecture: SQLite Index Cache
* **Paradigm:** Local-First Write-Ahead Logging (WAL).
* **Execution:** Disconnects slow disk I/O operations from presentation frames. Reads hit an in-memory SQL relational index cache instantly, while system changes drop data to source-controlled Markdown tracker layout files asynchronously via separate worker execution tracks.
