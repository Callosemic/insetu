# **Yomama Sync Bridge Engine v3: Complete Architectural Specification & Implementation Blueprint**

---

## **1. Executive Vision & Architectural Goals**

The **Yomama Sync Bridge (v3)** is the primary operational gateway for receiving LLM-generated patch payloads and applying structural mutations to local workspace files.

This specification establishes an interactive, **4-Phase In-Memory Compiler Pipeline** backed by an atomic Virtual File System (VFS) commit layer. It deprecates sequential per-file disk writes in favor of a zero-disk-write transactional lifecycle: **nothing touches the physical disk until 100% of selected patches are fully resolved, confirmed, syntax-validated, and unflagged (`can_commit: true`)**.

This document supersedes all previous standup blueprints (*2026-07-14: 3-Pass Compiler & Ephemeral Ledger* and *2026-07-21: Relocation/AST Expansion*).

---

## **2. System Responsibilities & Domain Boundaries**

To preserve strict Inversion of Control (IoC) and prevent logic leaks between the presentation layer and the kernel, responsibilities are partitioned as follows:

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │                      FRONTEND UI (bridge.js)                           │
 │  • String healing (repairing >>>>>>> REPLACE, stripping fluff)          │
 │  • Patch block splitting, select/deselect state management             │
 │  • Batch payload compilation and interactive action resubmission       │
 └──────────────────────────────────┬─────────────────────────────────────┘
                                    │ (Batch Payload + Selection Array)
                                    ▼
 ┌────────────────────────────────────────────────────────────────────────┐
 │                   BACKEND KERNEL (engine_bridge.py)                    │
 │  • 4-Phase In-Memory Pipeline (Zero Disk Writes during evaluation)     │
 │  • Candidate ranking, Yo-Ma-Ma expansion checks, AST syntax gates      │
 │  • SHA-256 disk hash lock & atomic VFS flush (vfs.save())              │
 └────────────────────────────────────────────────────────────────────────┘

```

### **A. Frontend Layer (`bridge.js` & `InSetuExtBridge`)**

* **Pre-Flight String Healing:** Parses raw LLM text streams to repair malformed markers (e.g., spaced `> > > > > REPLACE` lines), trims conversational prose before/after patch blocks, and normalizes indentation decay.


* **Batch Assembly & Selection State:** Manages the toggle state (`active: true/false`) for individual patch chunks and groups them by target file.


* **Interactive UI Resolution:** Renders interactive resolution cards for candidate selection, deep search authorizations, Yo-Ma-Ma expansion confirmations, and syntax error overrides.



### **B. Backend Kernel (`engine_bridge.py` & `bridge_vfs.py`)**

* **In-Memory Accumulating Workspace:** Evaluates all active patches in an in-memory Virtual Workspace buffer. Patch #2 evaluates against the updated memory buffer produced by Patch #1.


* **Candidate Scoring & Path Matching:** Runs ranked path alignment heuristics and candidate scoring across active repository bounds.


* **Safety & Syntax Verification:** Executes Yo-Ma-Ma expansion checks and passes full composed file buffers through native language AST parsers (`ast.parse()`, `node -c`, `json.loads()`).


* **Atomic Settlement:** Executes `vfs.save()` in a single atomic batch **only** when all patches pass without unconfirmed warnings or errors (`can_commit: true`).

## **3. The 4-Phase Pipeline Algorithm ($a.0$ through $i$)**

```text
  [ Incoming Patch Batch ]
             │
             ▼
 ┌───────────────────────┐
 │  Phase 1: Resolution  │ ──► Steps a.0 ➔ g (Path Alignment & Candidate Scoring)
 └───────────┬───────────┘
             │
             ▼
 ┌───────────────────────┐
 │   Phase 2: Safety     │ ──► Step h (Yo-Ma-Ma Expansion & Code Removal Inspection)
 └───────────┬───────────┘
             │
             ▼
 ┌───────────────────────┐
 │   Phase 3: Parsing    │ ──► Step i (Full-File AST Syntax Gate)
 └───────────┬───────────┘
     │
     ├──► IF Action Required OR Errors Found OR Dry-Run Mode:
     │        └─► ABORT COMMIT & RETURN JSON TELEMETRY
     │
     └──► IF 100% Resolved & Validated & Live Mode:
       │
       ├──► PHASE 4: ATOMIC VFS COMMIT (vfs.save())
       │
       └──► PHASE 5: LEDGER STAGING (zlib snapshot & SQLite tracking)
```
---

### **Phase 1: File & Path Resolution ($a.0$ – $g$)**

For each active patch in the batch, the engine attempts path resolution using the following hierarchy:

#### **Step $a.0$: Genesis Patch Check (Empty Search Block)**

* If `search.strip() == ""` (new file creation):
1. Verify if the target path resolves to an existing directory structure.
2. If the path fails to resolve, test `pinned_repos + path` or `pinned_repos - (.*?) - path`. If a valid directory matches, return a **`confirm-to-resolve`** prompt.
3. If a file **already exists** at the target destination, return a **`confirm-to-overwrite`** warning.



#### **Step $a.1$: No-Op & Idempotency Filter**

* Compare `search` and `replace` blocks using `is_effectively_identical()` (ignoring net-zero whitespace/indentation shifts).


* If identical, mark the patch as **`auto-skip`** and exclude it from the active transaction buffer.



#### **Step $b$: Direct Path & Filename Match**

* Test the exact filepath provided in the `<<<<<<< FILE:` header against disk/VFS.


* **Search Block Test:** If `search` matches the target file buffer $\rightarrow$ **Resolved!**

* **Replace Block Test:** Else if `replace` matches the target file buffer $\rightarrow$ The patch is already applied! Mark as **`auto-skip`**.



#### **Step $c$: Single Pinned Repo Shortcut**

* If **exactly one repository** is pinned in the active workspace context:
* Test `pinned_repo + path`.


* If `search` matches $\rightarrow$ **Auto-resolve** and attach an informational tag (`"Auto-resolved via pinned repo"`).


* Else if `replace` matches $\rightarrow$ Mark as **`auto-skip`** (already applied).





#### **Step $d$: Multi-Match Path Scoring & Ranking**

* Search across all workspace files matching the target filename (filtered by active repository pins).


* Score and rank candidate files based on path suffix alignment and `search` block matching.


* If candidate matches are found $\rightarrow$ Mark status as **`needs_confirmation`**, returning the ranked list of candidates with a pre-selected top match for user confirmation (`confirm-to-resolve`).

#### **Step $e$: Multi-Match Replace Fallback**

* Repeat step $d$ using the `replace` block instead of the `search` block.
* If candidate matches are found $\rightarrow$ Return a **`confirm-to-resolve`** prompt, but flag the status as **`already_applied`**.

#### **Step $f$: User-Authorized Deep Search (Gated)**

* **STRICT GUARDRAIL:** Deep workspace text search **must never execute automatically**.
* If filename and path matching fail entirely ($a.0 \rightarrow e$), halt resolution for this patch, mark its status as **`offer_deep_search`**, and return the patch to the UI.
* **When authorized by the user:**
1. Extract non-trivial lines from the `search` block (filtering out generic imports, lone brackets, and standard returns).
2. Use the longest unique line as a fast initial file filter across the workspace.
3. Verify candidate files by testing if the **full `search` block** matches inside them.
4. Return all fully-matched candidate files to the UI with interactive `[Resolve to File]` buttons.



#### **Step $g$: Resolution Failure**

* If Deep Search fails or is declined $\rightarrow$ Mark the patch status as **`failed`** with a descriptive error message and abort the transaction.

---

### **Phase 2: Patch Safety & Recursion Inspection ($h$)**

Once a patch is resolved to a target file buffer, the engine inspects the structural relationship between its `search` and `replace` blocks:

* **The "Yo-Ma-Ma" Expansion Check (`search` is inside `replace`):**
* Detects recursive expansion risks (e.g., repeatedly applying a patch that wraps code).
* **The Nuance Rule:**
* If `search` is inside `replace`, BUT the full `replace` block **does NOT exist in the code** $\rightarrow$ This is a legitimate code wrapper or addition. **Safe! Proceed without flagging.**
* If `search` is inside `replace`, AND the full `replace` block **ALREADY exists in the code** $\rightarrow$ **Expansion Risk!** Flag status as `needs_confirmation` and return prompt: `[Looks patched already: Confirm / Deselect Patch]`.




* **Code Removal Check (`replace` is inside `search`):**
* Detects net-code deletion. Attach an informational **`code_removal`** flag and proceed automatically.


* **Distinct Substitution:**
* Clean `search` $\rightarrow$ `replace` swap. Proceed without flags.





---

### **Phase 3: Full-File AST Syntax Gate ($i$)**

The engine applies the patch in memory to a copy of the file buffer. If the file extension is mapped to a language parser, the **entire composed file buffer** is validated:

* **Python (`.py`):** Validated via `ast.parse()`.


* **JavaScript / TypeScript (`.js`, `.ts`):** Validated via `node --input-type=module -c`.


* **JSON (`.json`):** Validated via `json.loads()`.


* **Non-Code / Templates (`.md`, `.html`, `.txt`, `.yaml`):** Gracefully bypass Phase 3.



If validation fails:

1. Capture the syntax error message and line number.


2. Generate a Base64-encoded diff (`diff_b64`) showing the error location.


3. Set patch status to **`syntax_error`** and provide available UI actions: `[Ignore Syntax Error]` or `[Cancel & Deselect Patch]`.

---

### **Phase 4: Disk Hash Lock & Settlement**

Nothing is written to physical storage during Phases 1–3.

* **SHA-256 Disk Hash Concurrency Guard:**
* During evaluation, the backend computes a `SHA-256` hash of every target file on disk (`disk_hash`).
* When the user submits interactive confirmations, the backend verifies `current_disk_hash == evaluation_disk_hash`. If an external process modified the file in the background, the transaction is rejected and re-evaluated.


* **Dry-Run Mode:**
* Executes the **exact same 4-phase pipeline** (including path scoring, Yo-Ma-Ma checks, and AST parsing).


* Returns the full JSON telemetry report without invoking `vfs.save()`.
* **Live Mode Settlement:**
* If and only if **`can_commit: true`** (100% of active patches are resolved, valid, and unflagged), all modified memory buffers are committed to the Virtual File System in a single atomic flush (`vfs.save()`).

---

### **Phase 5: Ledger Staging & Telemetry**

Synchronous with the atomic VFS flush, the engine maintains an Event-Sourced Ephemeral Ledger to provide absolute safety against logic drift and destructive AI writes.

* **The `bridge_ledger` Schema:** Patch history is recorded into the centralized `workers.db` SQLite database. This tracks `patch_id`, `transaction_id`, `search_block`, `replace_block`, and `post_patch_hash`.
* **`zlib` Snapshots & The Human Intercept Rule:** Before applying a patch, the engine compares the current disk hash against the last known hash in the ledger. If the user made manual edits between prompts (`current_disk_hash != last_known_hash`), the engine compresses the current raw file state via `zlib` and writes an emergency baseline snapshot row.
* **Forward-Replay Reversion:** Rather than relying on reverse deltas, rollbacks are handled by pulling the last `is_snapshot == true` row, inflating it back into text, and deterministically applying all stored `search`/`replace` blocks forward chronologically up to the targeted turn.
* **Metronome TTL Housekeeping:** A background worker task sweeps the ledger and drops historical rows older than 48 hours (`ttl_expires_at`) post-Git push, keeping the database footprint compact and fast.

## **5. Frontend UI Integration & History**

A dedicated **History** sub-tab is mounted via the core extension registry to provide visual oversight over the ledger.

* **Transaction Turns View:** Displays a chronological vertical timeline of patch records. Multi-file patches are grouped under single transaction cards displaying file counts, timestamps, and inferred commit messages.
* **Visual Diff Modal:** Clicking an active turn card launches a full-viewport `<insetu-modal>` displaying a side-by-side or inline code comparison canvas, allowing operators to review success/danger diffs before confirming a forward-replay rollback.


### **Status Field Enumeration**

* **`resolved`:** Path and patch fully validated without issues.
* **`auto_skipped`:** No-op or already applied (`replace` block matched).


* **`needs_confirmation`:** Ambiguous path, overwrite warning, or Yo-Ma-Ma expansion risk.
* **`offer_deep_search`:** Path resolution failed; waiting for user to authorize deep search.
* **`syntax_error`:** Patch applied in memory, but AST/language validation failed.


* **`failed`:** Unresolvable or fatal error.

## **7. Edge Cases & Safeguards Matrix**

| Edge Case | Identified Risk | Architectural Safeguard |
| --- | --- | --- |
| **Code Wrappers** | Wrapping code in `try/except` embeds `search` inside `replace`. | Check if `replace` **already exists** in code. If not present $\rightarrow$ Safe, proceed without flagging. |
| **Inter-Patch Batch Dependencies** | Patch #2 targets a file created or moved by Patch #1 in the same batch. | Maintain an **accumulating in-memory Virtual Workspace**. Patch #2 evaluates against Patch #1's updated memory buffer. |
| **Line Ending Drift (CRLF vs. LF)** | Windows `\r\n` vs Unix `\n` causes string matching failures.

 | Normalize all buffers to `\n` in memory during Phase 1–3. Restore target file EOL format during Phase 4 disk flush.

 |
| **Boilerplate Deep Search Triggers** | Longest line is generic (e.g., `import React from 'react';`). | Filter out common syntax imports/returns. Fast-filter on candidate files, but **require full `search` block match** before presenting. |
| **Partial AST Syntax Failures** | Valid code snippets fail standalone AST parsing. | Perform AST validation **exclusively on the composed full-file buffer** after the patch is applied.

 |
| **Concurrent Disk Edits** | External process modifies file while user reviews UI confirmation. | Validate `current_disk_hash == evaluation_disk_hash` before committing confirmed patches. |
