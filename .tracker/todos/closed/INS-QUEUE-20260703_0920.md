## Description
To provide granular, atomic reversion between Git commits, we must implement a databased ledger of Yomama patches utilizing an **Event Sourcing with Snapshotting** architecture. 
This serves as a highly surgical "undo" tree for LLM hallucinations or logic drift that occurs before a developer is ready to formally stage and commit their working directory.

This is strictly an ephemeral patch history, not a secondary version control system.

### Execution Blueprint
1. **The SQLite Ledger (`bridge.db`):** Create a new table tracking `patch_id`, `repo`, `filepath`, `search_block`, `replace_block`, `post_patch_hash`, `is_snapshot` (BOOLEAN), `compressed_state` (BLOB), `timestamp`, and `ttl_expires_at`.
2. **The Sync Intercept (Write Path):** Update `execute_bridge_sync` in `engine_bridge.py` to calculate a SHA-256 hash of the target file prior to patching. 
    * **Snapshot Rule:** If `current_disk_hash != last_known_hash` (manual edits detected) OR `turns_since_last_snapshot >= 5`, create a baseline snapshot row using `zlib` compression.
    * Apply the patch, hash the result, and write the patch matrix row to the ledger prior to the VFS commit.
3. **The Git Push Hook:** Update `api_git_push` in `engine_git.py` to broadcast a `post_git_push` event over the Event Bus upon a successful remote sync.
4. **The TTL Expiration:** The Bridge extension listens for `post_git_push` and updates all active ledger entries for that repository with a `ttl_expires_at` timestamp (e.g., NOW() + 48 hours).
5. **The Metronome Sweep:** A background worker routine periodically sweeps the `bridge_ledger` table, permanently dropping rows where `NOW() > ttl_expires_at`, keeping the SQLite footprint mathematically bounded and preventing infinite disk bloat.
6. **The History UI:** Register a new `History` sub-tab under the `Edit` workspace via `ExtensionRegistry.registerSubTab()`. This view queries the SQLite ledger and displays recent patches chronologically.
7. **The Forward-Replay Revert:** When "Revert to Turn X" is clicked, the engine abandons backward mathematical inversion in favor of deterministic forward-playback:
    * Query the nearest preceding row where `is_snapshot == True`.
    * Decompress the snapshot state into an in-memory string.
    * Chronologically apply the cached `search_block` / `replace_block` matrices up to Turn X.
8. **The VFS Commit:** Because the historical patches already passed AST/Fuzzy validation during their original execution, the final assembled string bypasses standard validation and is piped directly into the `_VFS_WRITE_QUEUE` for absolute deterministic reliability.
